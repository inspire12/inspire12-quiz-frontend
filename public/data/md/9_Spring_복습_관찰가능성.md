1. 로깅과 모니터링의 목적 중 잘못된 것은?
A. 시스템의 문제를 조기에 탐지함
B. 사용자 행동을 기반으로 기능 개선에 활용됨
C. 성능 측정을 위한 지표 수집이 가능함
D. 비즈니스 로직 구현을 자동화함

정답: D
해설: 로깅과 모니터링은 관찰을 위한 도구일 뿐, 자동 구현 기능은 아님.
출제의도: 관찰 가능성 개념이 자동화와는 다르다는 것을 구분할 수 있는지 확인.

2. DDD에서의 ‘정책(Policy)’에 대한 설명 중 틀린 것은?
A. 특정 이벤트에 자동으로 반응하는 규칙임
B. ‘~하면 ~한다’ 형태의 명시적인 로직으로 표현됨
C. 유저의 요청이나 입력을 직접 받는 역할임
D. 이벤트 발생 후 이어지는 비즈니스 흐름을 정의함

정답: C
해설: 유저의 직접 요청은 Command의 역할임. 정책은 도메인 이벤트 이후 조건적 흐름을 담당함.
출제의도: 도메인 구성요소 간의 역할 구분이 정확한지 검증.

3. 이벤트 스토밍에서 ‘도메인 이벤트’로 보기 어려운 것은?
A. 주문이 완료됨
B. 결제가 실패함
C. 사용자가 로그인함
D. 주문을 요청함

정답: D
해설: “주문을 요청함”은 **Command(명령)**임. 도메인 이벤트는 ‘~됨’처럼 과거형으로 발생한 일을 표현함.
출제의도: 이벤트 스토밍 구성요소의 표현 방식과 의미 차이를 인지했는지 확인.

4. 아래 중 관찰 가능성(observability) 구성 요소로 보기 어려운 것은?
A. Logs
B. Metrics
C. Traces
D. Threads

정답: D
해설: 관찰 가능성의 핵심은 Logs, Metrics, Traces임. Threads는 운영체제 수준의 개념이며 observability 구성 요소는 아님.
출제의도: 관찰 가능성 3요소에 대한 정확한 식별력을 확인하기 위함.

5. TDD의 한계 또는 단점으로 보기 어려운 설명은?
A. 테스트 시나리오를 먼저 고민해야 하므로 시간이 더 소요됨
B. 잘못된 테스트 작성은 오히려 개발을 지연시킬 수 있음
C. 명확한 요구사항 없이도 빠르게 코드를 구현할 수 있음
D. 변경된 비즈니스 로직에 따라 테스트 코드도 유지보수 필요

정답: C
해설: TDD는 명확한 요구사항(명세)이 있어야 가능한 방식임. 요구 없이 빠르게 구현하는 건 오히려 반 TDD에 가까움.
출제의도: TDD의 **전제 조건(요구사항 기반 설계)**이 무엇인지 이해했는지 판단.
