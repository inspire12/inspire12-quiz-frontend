1. 테스트 코드의 특징으로 보기 어려운 것은?
A. 반복적으로 실행 가능해야 한다
B. 문서화 기능을 제공할 수 있다
C. 테스트 환경은 실제 운영 환경과 동일해야 한다
D. 비즈니스 로직의 흐름을 코드로 표현할 수 있다

정답: C
해설: 테스트 환경은 운영 환경과 구분된 격리된 환경에서 실행해야 함. 실제 운영 환경에서 테스트하면 예기치 못한 문제가 발생할 수 있음.
출제의도: 테스트 코드 작성 시 환경 격리 원칙을 알고 있는지 확인.

2. 단위 테스트를 작성할 때 사용하는 Given-When-Then 패턴 중 틀린 설명은?
A. Given: 테스트 준비 단계, 입력 데이터 구성
B. When: 테스트 실행 단계
C. Then: 결과 비교 및 검증 단계
D. Where: 예외 발생 여부를 체크하는 단계

정답: D
해설: Where는 GWT 패턴에 존재하지 않음. 예외 검증은 Then 또는 assertThrows에서 다룸.
출제의도: 테스트 패턴의 기본 구조를 혼동 없이 알고 있는지 평가.

3. 다음 중 AssertJ의 장점으로 보기 어려운 것은?
A. 예외 발생을 try-catch 없이 테스트할 수 있음
B. 조건별로 다양한 assert 구문을 제공함
C. IDE의 자동완성과 가독성이 좋음
D. 테스트 실행 결과에 따라 자동 리팩토링을 수행함

정답: D
해설: AssertJ는 자동 리팩토링 기능은 없음. 테스트 코드 작성의 편의성을 제공하는 도구임.
출제의도: 테스트 도구에 대한 기능적 기대치를 정확히 알고 있는지 확인.

4. TDD의 장점으로 보기 어려운 설명은?
A. 명세 기반 개발이 가능해짐
B. 테스트가 먼저 있어야 로직을 더 안정적으로 작성할 수 있음
C. 모든 비즈니스 로직을 자동으로 생성할 수 있음
D. 리팩토링 시 회귀 테스트 역할을 수행함

정답: C
해설: 로직 자동 생성은 TDD의 기능이 아님. TDD는 명세 기반 구현 → 리팩토링 → 안정성 확보를 위한 개발 방식임.
출제의도: TDD의 본질과 오해되는 기능을 구분할 수 있는지 확인.

5. 도메인 주도 설계(DDD)와 관련하여 틀린 설명은?
A. 도메인을 중심으로 비즈니스 로직을 설계함
B. 엔티티, 밸류, 애그리게잇 등 도메인 모델을 명확히 나눔
C. 기술적인 구조보단 비즈니스 개념을 먼저 고려함
D. 테스트보단 실서비스 구현이 우선임

정답: D
해설: DDD는 비즈니스 중심 설계를 위해 테스트 기반 설계가 강조됨. 실서비스보다 도메인, 테스트, 명세가 선행됨.
출제의도: DDD의 절차와 철학을 이해하고 있는지 확인.
